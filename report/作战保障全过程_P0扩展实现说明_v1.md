## 2. 后端改动（均在 `src/brigsim/support/`）

### 2.1 `battle_loss.py` 新增三个纯派生函数

- **`rates_both_doctrines(loss, core_rates)`**：在 `rates_from_loss_list`（口径 A）基础上并列给出口径 B。
  - 口径 A（权威）：战损率只认 K 级，与内核 `attrition_red` 等价，可对账。
  - 口径 B（辅助）：战斗损伤率 = K+M+F，反映广义受损，**不对账内核战损率**。
  - 输出 `doctrines[]`（含 `authoritative`/`reconcilable` 标记）+ `rate_basis_default="A"`。
- **`replication_ci(rows)`**：输入 `run_replications` 的逐次指标列表，输出逐次明细 + 每个指标 mean/std/ci95/lo/hi；
  95%CI 采用 z=1.96·sd/√n，与 `experiment/metrics.summarize` 口径完全一致。success 单列"成功数/总数"。
- **`business_timeline(snap_df)`**：从事件快照逐 tick 派生**业务环节流转**（受损发现→损伤评估→分级判定→抢救抢修→后送处置→修复归队→报废补充），
  输出每单位的事件轨迹与环节计数。这是与"软件 8 节点流程条"并列的第二条主线，纯展示、不影响四率。

### 2.2 `api.py`

- `_deduce_worker` 在推演完成后把 `rows` 存入 `loss["replication"]`、事件帧派生结果存入 `loss["timeline"]`，
  并把主对账从 `rates_from_loss_list` 换成 `rates_both_doctrines`（A 仍是权威对账基准）。
- `loss_get` 无需改（打包在整个 loss 里回传）。
- `export` 新增 `what="plan_docx"`：调用 `plan.to_docx_bytes()`，base64 回传，前端 Blob 下载，不改服务静态路由。

### 2.3 `mission_input.py`

- `validate` 新增 `targets` 对象（readiness/success/repair_timeliness，自动补 `%`），缺省 90/85/80%，不进内核。

### 2.4 `plan.py`

- `build_slots` 的 3 个目标阈值槽位改为从 `mission.targets` 读取（原来硬编码 90/85/80%）。
- 新增 `build_provenance(slots, text)`：77 个槽位里所有确定性数值槽位 → 来源/定义/取值/是否出现在正文，
  结果挂在方案 `provenance` 字段；LLM 叙述槽位不进溯源（不产生权威数字）。
- 新增 `to_docx_bytes(plan)`：自包含公文式 docx（A4/仿宋四号/黑体标题/固定行距），
  不 import `report/build_report_docx.py`（避免其 argv 副作用）。

### 2.5 `server.py`

**本批未改动**（docx 走已有 `/api/support/export` POST，口径/CI/时间线走已有 GET/POST 路由）。

## 5. 数据口径与诚实限制

1. **口径 A/B 在本想定下数值相同**：终态快照的 `damage_grade` 多为 0(N，含已修复) 或 3(K)，M/F 属中间态很少出现在终态，
   故 `K+M+F` 恰等于 `K`。口径 B 的实现正确（单测用构造数据验证 A=0.2/B=0.6），差异取决于想定数据本身，不虚构 M/F。
2. **环节时间线的部分轨迹显示"状态更新"**：当 `part`/`disposition` 在终态快照中无变化点时，只能派生出"受损发现"，
   无法反推未记录的中间环节——宁可标"状态更新"也不虚构环节。这是事件流保真，不是缺陷。
3. **CI 为正态近似**：z=1.96·sd/√n，与项目既有 `metrics.summarize` 一致；小样本(如 n=4)区间较宽属正常。
4. **docx 为公文式排版**：复用报告版式规范，但表格样式为简化实现（正文内保留 markdown 表格文本），与正式公文表格细节略有差异。
