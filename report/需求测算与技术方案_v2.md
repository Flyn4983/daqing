## 1. 需求理解

- **需求 A（一致性）**：软件流程/细节/数据与最终文档逐项对应，评委照文档念的那句话，软件上能立刻指到且数字一致。
- **需求 B（架构改造）**：软件从"模拟推理"升级为"真实调用本机大模型"，计算完毕后把结构化结果交给本地大模型生成可解释、可追溯的方案。

## 3. 技术方案

### 3.1 总体架构（同机双进程，零外网）

```
浏览器(前端大屏) ─HTTP→ AgentWebServer(8848) ──HTTP 回环──→ 本地大模型推理服务(8000, OpenAI兼容)
                            │
                            ├ engine: 意图路由 + 工具调度（代理/Pareto/守卫，数据全部真实）
                            ├ service: 推理状态机（真实模式读数 from /metrics 或估算）
                            └ 新增: llm_client 适配层（可插拔，配置驱动）
```

### 3.2 B1 本地大模型适配层（可插拔，配置驱动）

- 新增 `src/brigsim/agent/llm_client.py`：`LocalLLMClient`，走 OpenAI 兼容 `POST {base_url}/chat/completions`，`stream:true` 可选。
- 配置源（优先级：环境变量 > `llm_config.json` > 默认值）：
  - `BRIGSIM_LLM_BASE_URL`（默认 `http://127.0.0.1:8000/v1`）
  - `BRIGSIM_LLM_MODEL`（默认 `Qwen3-32B`）
  - `BRIGSIM_LLM_API_KEY`（默认 `EMPTY`）
  - `BRIGSIM_LLM_TIMEOUT`（默认 60s）
  - `BRIGSIM_LLM_MODE` = `real` | `mock` | `auto`（auto：探测失败自动降级 mock，现场不翻车）
- 统一接口：`chat(system, messages, tools_schema) -> {text, tool_calls, usage}`；`is_available() -> bool`。
- vLLM / Ollama(`/v1`) / LM Studio 均符合 OpenAI 协议，框架后定不改代码。

### 3.3 B2 计算完毕后触发链（真实方案制定）

1. 前端"一键生成" → `POST /api/plan {tag}`；
2. `engine` 先调用真实工具链（`generate_support_plan` → 代理预测 + Pareto + 守卫复验）得到 **结构化真实结果**；
3. 组装 prompt：系统角色 = 装备保障参谋；上下文 = 该方案的真实数字（决策/四率/成本/复验/约束）；指令 = 输出可解释、可追溯的方案（含参数表、依据、风险）；
4. 调 `LocalLLMClient.chat()`；流式回传或一次性返回；
5. 前端展示：真实数字表格（来自步骤2，保证与文档一致）+ 大模型生成的解释文本；
6. 任何环节失败 → 自动降级到现有 `_render_plan` 模板，并在角标提示"本地模型未就绪，使用内置模板"。

### 3.4 B3 状态面板真实读数

`/api/status` 的 model/device/vram/util/requests 在 real 模式下改为读本地推理服务（vLLM `/metrics` 或 `/v1/models` + 本地实测延迟）；mock 模式维持原确定性模拟。`backend` 字段显式标注 `真实本地推理` / `模拟`。

### 3.5 A1 η 战力再生卡

- 公式（文档式1）：`η = ω₁R₀ + ω₂(1−A) + ω₃Pᵣ + ω₄(1−F)`，F 以基线故障率归一化。
- 反推权重（用实测 baseline/knee 数据拟合，精确复现 0.488→0.491）：
  `ω ≈ [0.355, 0.153, 0.398, 0.094]`（保留4位，可微调）。
- 前端新增 KPI 卡：η 现值 + 基线→推荐变化；指标分解小条（四率分项贡献）。

### 3.6 A2/A3 口径标注与模块映射

- knee 方案卡：`success 0.7104` 标注"代理预测值"，旁注"终审 130/200 = 0.650（文档口径）"。
- 新增"功能对照"入口：文档 5 模块 / 4 域 9 功能 ↔ 界面位置映射表（可点定位）。
