# 界面功能扩展与信息架构优化建议 v1

> 基于对现有代码逐文件核查（2026-11-21），非凭印象推演。目标：在**不动仿真内核、不破坏原有核心流程**的前提下，补全输入项、配置项、筛选条件与功能点，并给出可承载后续扩展的信息架构（IA）方案。
> 本文只做分析与建议，**未改动任何代码**。

---

## 0. 结论摘要

平台现有能力已覆盖"录入→多次推演→战损清单→指标派生→方案生成"主链路，但存在三类问题：

- **语义错位**：名为"作战保障全过程"的流程条其实是软件数据处理管线，不是真实保障业务环节的衔接与状态流转——而这正是你最核心的意图。
- **能力闲置**：战损清单的多维汇总后端已算好，前端只展示 9 列、截前 400 条；CLI 有均值±95%CI，Web 全过程没有。
- **入口混杂**：4 个顶栏入口混用了页面/抽屉/模态语义，配置弹窗与录入抽屉构成双重数据源。

建议分三层推进：**P0 补主链路缺口（8 项）→ P1 增强可用性与可信度（8 项）→ P2 进阶能力（7 项）**。若只做 P0，现有两页勉强可承载；要做 P1/P2，必须按本文 §6 重构为"1 驾驶舱 + 1 作业中心 + 1 知识中心 + 1 全局抽屉"的分层导航，否则信息架构会失控。

**展示项现状**：四率卡、时序曲线（4 指标×红蓝×方案切换）、MC 分布、3D 回放+图例+播放控制、Pareto、Sobol、代理 parity、指标卡、9 列清单表、方案正文、对账通过标记。

### 1.3 三个关键洞察

1. **流程条语义错位（最关键）**：`PROCESS_NODES` 的 8 节点是"软件数据处理步骤"（INPUT/VALIDATE/DEDUCE/LOSS/METRICS/PLAN/REVIEW/EXPORT），不是"部队保障业务环节"（发现战损→上报→损伤评估→分级判定→现地抢修/拖救/后送→器材补给→修复归队）。你要求"清晰呈现各节点式环节、环节之间的衔接关系与状态变化"，目前只呈现了前者。建议新增**业务环节状态时间线**作为与流程条并列的第二条主线。
2. **后端汇总能力闲置**：`aggregate()` 已产出 6 个维度的汇总，前端清单表一个都没用；CLI 有"均值±95%CI"，Web 全过程只显示单次结果。
3. **双重数据源**：`config-modal` 的保障 7 旋钮与 `sf-drawer` 的录入映射是两套入口，容易让用户困惑"到底在哪改才生效"。

## 3. P0 重点项落地说明

### P0-5 业务环节状态时间线（最能体现核心意图）

现状：`PROCESS_NODES` 8 节点是"软件在做什么"，用户想看的是"部队保障在做什么"。建议新增与流程条并列的第二条主线，用泳道图呈现：

```
单位编号 → [发现战损] → [上报] → [损伤评估 M/F/K] → [分级处置]
                                        ├─ M → [现地抢修] → [修复归队]
                                        ├─ F → [拖救/后送] → [后方修理] → [归队]
                                        └─ K → [判定报废] → [补充置换]
                              ↓ 贯穿：[器材前送] [弹药补给] [油料补给]
```

- 数据来源：事件流已有 `damage_grade / part / disposition / tick / weapon / unit_id`（`kernel/events.py`），逐件清单已有 `repair_status/location`。
- 状态变化：每个环节的进入/退出 tick 可从事件流派生，用颜色+时间轴表达"环节衔接与状态变化"。
- 不影响内核：纯前端/展示层派生，不改四率。

### P0-1 + P0-2 + P0-3 战损清单区改造（一个子页解决三项）

把中栏"战损清单"区改造成带子 tab 的分析面板：

| 子 tab | 内容 | 复用后端 |
|---|---|---|
| 逐件清单 | 9 列 + 筛选（阵营/等级/处置/类别/平台/部位/时间窗）+ 排序 + 分页 | `loss.items` |
| 多维汇总 | 等级/类别/处置/阵营 4 组柱饼图 | `summary.by_*`（已算好） |
| 复制明细/CI | N 次复制逐行 + 均值±95%CI | 需后端补 API（复现 `experiment` 汇总逻辑） |
| 对账明细 | 清单值/内核值/差异/容差 展开表 | `rates.reconciliation` |

### P0-4 口径切换的边界（重要）

分析报告已明确：**口径 A**（战损率只认 K）与现有 `1-alive_n/n` 完全等价，可安全切换；**口径 B**（含 M/F）会改变权威数字，只能作为"战斗损伤率"另列，不能顶替战损率。建议开关做成"战损率口径=A（默认，可对账）/ A+B 双列展示"，并在 UI 明确标注哪种是权威口径，避免与报告数字打架。

## 4. 信息架构（IA）方案

### 4.1 现有两页承载评估

| 扩展批次 | 塞进"态势驾驶舱" | 塞进"保障全过程抽屉" | 结论 |
|---|---|---|---|
| P0（8 项） | 仅 P0-7/8 的展示部分可融入 | 其余 6 项可吸收（加筛选条、子 tab、汇总图、开关） | **勉强可承载**，但左栏录入会更长 |
| P1（8 项） | 几乎不可（无空间） | 模板管理/LLM 参数/档案列表塞入会过载 | **需新增面板或浮层** |
| P2（7 项） | 不可 | 不可 | **必须重构导航** |

结论：**只做 P0 可维持现状；要做 P1/P2 必须重构 IA**，否则顶栏入口与抽屉内容会指数级膨胀。

### 4.2 问题诊断

1. 顶栏 4 个入口语义混杂：`保障全过程`(抽屉)、`功能对照`(模态)、`研究细节`(模态)、`智能参谋`(抽屉) 混排，用户难以形成"我在哪个模块"的心智模型。
2. 浮层过多：1 配置弹窗 + 2 全屏抽屉 + 2 模态，层级关系不清晰，Esc/关闭行为不统一。
3. 双重数据源：配置弹窗与录入抽屉都能改保障参数，职责重叠。
4. 无"作业归档"层：每次推演/方案是即刻消费，缺少可回溯的工作空间。

### 4.3 推荐方案：四区分层导航

```
顶栏一级导航（分段控件，取代现有 4 个混杂按钮）
┌ 态势驾驶舱 ┬ 保障作业中心 ┬ 知识与口径 ┐        [智能参谋]（全局右侧抽屉，任意视图可唤起）
│  (默认首页) │   (核心作业)  │  (静态说明) │
└────────────┴──────────────┴─────────────┘
      │              │               │
      │              ├ ①任务与编成录入（含双方实力、目标阈值、口径开关）
      │              ├ ②推演配置与执行（种子/CI/LLM参数/7旋钮）
      │              ├ ③战损清单与指标（子tab：逐件/汇总/CI/对账/环节时间线）
      │              ├ ④方案编制（模板管理/槽位映射/叙述覆写/数字溯源/docx导出）
      │              └ ⑤作业档案（快照列表/版本对比/批量工况对比）
      │
      └ 现有三列主网格完全保留（KPI/四率/时序/MC/3D/Pareto/Sobol/代理），一个不动
```

**导航规则**：
- 一级最多 3 个视图，二级最多 5 个作业步；层级不超过 2 层。
- 8 节点流程条保留，作为"保障作业中心"内部 ①~④ 的状态驱动指示器（点击跳对应步），语义从"软件管线"升级为"作业步骤条"。
- 业务环节状态时间线（P0-5）作为独立可视化，与流程条并列，专门表达"业务环节衔接与状态"。
- 智能参谋保持全局抽屉，任何视图可唤起，不占导航位。
- 配置弹窗的保障参数并入②推演配置，天候/地形并入工况选择，消除双重数据源。

### 4.4 保守备选方案（若暂不重构）

保留现有顶栏 4 按钮 + 主网格，仅做两点：
1. 顶栏增加一个「更多 ▾」下拉，收纳功能对照/研究细节/数据字典等静态入口；
2. 保障全过程抽屉内把三栏改为"左侧步骤导航 + 右侧内容区"，内容区按 ①~⑤ 切换，避免单栏塞入所有扩展。

优点：改动小、核心流程零风险；缺点：仍保留浮层混杂，P2 能力难以优雅承载。

## 5. 确保功能扩展不影响原有核心流程
