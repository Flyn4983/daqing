> 编制日期：2026-11-21
> 依据：① 现有源码实证（`C:\Users\flyn4\Desktop\daqing\src\brigsim\**`，逐文件核对）；② 公开条令/训练资料（国防部、人民网、解放军报相关报道，"战术级后勤保障计划九项内容""战时装备保障指挥四项任务""模块化编组""损伤评估→抢修/拖救→后送→器材前送"链路）；③ 现有四率口径（`docs/data-interface.md`、`experiment/four_rates.py`）。

### 1.2 业务对齐：合成旅保障规则化流程 → 平台映射

公开资料显示，合成旅（旅基）装备保障的典型规则化流程为：

```
战前筹划（实力统计/战损预计/储备标准/力量编组与配置）
   ↓
战中实施：一线报损 → 损伤评估 → 分级处置
   ├─ M 微损 → 现地抢修 → 归建
   ├─ F 重损 → 拖救/后送 → 后方修理所 → 归建/补充
   └─ K 战毁 → 报废 → 补充/拜占 (writeoff)
   ↓
持续保障：器材前送 / 弹药前送 / 油料补给 / 油料与抢救力量运用
   ↓
阶段/战后：战损统计 → 保障总结 → 方案修订
```

| 业务环节（公开条令口径） | 平台现状 | 对齐结论 |
|---|---|---|
| 装备实力统计与编成录入 | YAML 已有，Web 无图形化录入 | 部分对齐，需补录入界面 |
| 战损预计（战前） | 代理模型可预测四率，但无"按装备型号的战损数量预计表" | 部分对齐，清单可补 |
| 一线报损/损伤评估 | 内核 `DamageModel.resolve_hit` 自动判 M/F/K 与部位 | ✅ 内核对齐（仿真替代人工报损） |
| 分级处置（现地修/拖救/后送/报废） | `disposition` 五档 + 拖救链 + 抢修队列 + 后送波次 | ✅ 内核对齐 |
| 器材前送（携行/运行/基地三级） | 三档储备 + 波次前送 + 缺件等待统计 | ✅ 内核对齐 |
| 弹药前送 | 弹药车 + 基数 + 弹种 | ✅ 内核对齐 |
| 油料保障 | 无 | ❌ 需新增模型与数据项 |
| 抢救抢修力量运用 | 7 旋钮中的 `red_repair_teams/red_arv/red_supply_veh` | ✅ 决策变量对齐 |
| 战损清单（逐件、分级、处置） | 仅事件流，未导出清单 | ❌ 核心缺口 |
| 战损统计与保障方案 | 有数值方案，无公文式方案 | ❌ 核心缺口 |
| 保障部署/防卫/通信/运输计划 | 无 | ❌ 需模板层补（可不进仿真内核，由方案模板组织） |

**判断**：平台定位应是"保障决策的量化推演与方案生成内核"，而非替代实兵指挥系统。因此对齐的正确姿势是——**用图形界面把真实业务的输入喂进来，用推演产出可作为战损统计底账的清单，再由大模型把清单+模板变成可签发的保障方案**；仿真内核只做"该改才改"。

### 1.3 输入侧差距

1. **能力错配**：现有配置弹窗看似开放 30+ 控件，真正改变仿真结果的仅 mission 4 项、红蓝 detect/speed 4 项、7+3 特征旋钮；地形/天气/能见度/风场控件在 live 推演路径被 `skip_terrain_env=True` 忽略（`server.py:891-894`）。需要明确这些控件的语义（是"预览用"还是"推演用"），不能让用户误以为改了会生效。
2. **粒度错配**：真实工作按"旅-营-连-排 → 单车/单装 → 弹药基数/油料携带量/器材箱"逐级录入；平台目前只有"平台类型 + 数量模板"，无"单车实名台账"和"物资品类表"。
3. **品类缺失**：油料、日常业务要素（战备等级、值勤、训练计划、请领审批、器材台账、维护保养）、通用消耗品（给养、被装、卫勤、工程器材）均无。
4. **入口缺失**：无"新建任务→录入编成与资源→保存想定→多次推演"的图形化工作流。

### 1.4 输出侧差距

1. **无战损清单**：这是最致命的一环。战损率由 `1 - alive_n/n` 直接算，没有一张"哪台车、什么型号、什么等级、怎么处置"的账，无法支撑人工复核、上报、补充决策，也无法作为方案生成的输入。
2. **口径待明确**：现有战损率只认 `alive=False`（即 K 级战毁），可修复的 M/F 不计入；分母 `n_by_side` 含 `apply_features` 新增的保障车实体。这与"战损清单"可能要求"按装备类别/按等级"统计不一致，必须先定口径（见 §4.3）。
3. **方案不是公文**：现状方案是"7 旋钮取值 + 四率对比 + 成本"的数值结果 + 一段大模型说明文字；缺少"情况判断—力量编组—抢救抢修—器材/油料/弹药补给—后送—防卫/通信—附表"的层级和表述。
4. **LLM 未真正参与生成**：LLM 只写"第五节说明"，数字全部由规则引擎给，且无函数调用、无结构化输出、无模板入口。

### 1.5 差距分级汇总

| 编号 | 差距 | 等级 | 是否影响权威数字 | 建议 |
|---|---|---|---|---|
| G1 | 无结构化战损清单 | **P0** | 否（清单从现有数据派生） | 新增清单生成器，作为四率的唯一事实源 |
| G2 | 无法图形化录入装备/弹药/油料/保障车辆/日常业务要素及数量 | **P0** | 否 | 新增"任务资源编辑器"，落盘为输入 JSON |
| G3 | 方案非公文式、无模板机制 | **P0** | 否 | 新增方案模板 + 槽位映射 + LLM 渲染 |
| G4 | 油料链缺失 | P1 | 否（当前四率不含油料） | 先作为"方案层数据项"，二期再进内核 |
| G5 | 地形/天气控件不生效的语义混乱 | P1 | 若放开会影响 | 明确标注"预览/推演"用途，或放开需重标定 |
| G6 | 日常业务要素缺失 | P1 | 否 | 作为输入数据项，用于方案上下文 |
| G7 | 多次推演无统一落盘明细 | P2 | 否 | 输出 `runs_detail.csv` + CI |

## 2. 功能改造范围

### 2.1 总体架构：新增三层，内核保持冻结

```
┌─────────────────────────────────────────────────────────────┐
│ A 输入配置层（新增）   任务资源编辑器（GUI）                  │
│   装备 / 弹药 / 油料 / 保障车辆 / 其他保障资源 / 日常业务要素  │
│   → 生成 mission_input.json（带校验）                        │
└───────────────────────────┬─────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ B 推演编排层（改造）   现有 run_replications 外包一层         │
│   mission_input → N 次推演 → 汇总 + 事件流                   │
└───────────────────────────┬─────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ C 战损清单层（新增）   ★唯一战损事实源★                      │
│   逐单位/逐装备 战损清单 + 按类别/等级汇总 + 四率由清单派生    │
│   → battle_loss_list.json / .csv                            │
└───────────────────────────┬─────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ D 方案生成层（新增）                                          │
│   数值方案(现有) ─┐                                          │
│   战损清单 ───────┼→ 槽位映射(确定性) → 正式模板 → LLM(叙述)  │
│   正式模板 ───────┘   → 校验(数字一致性) → 最终保障方案(.md/.docx) │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 输入侧改造（A 层）

1. **新增 Web 页签"任务资源编辑器"**：在 `#config-modal` 之外新增独立抽屉/页签，包含 6 个子页：装备编成、弹药、油料、保障车辆、其他保障资源、日常业务要素。每个子页支持"下拉选择标准项 + 数量输入 + 手动新增品类"，并实时显示合计与校验（数量为正整数、品类不重复、装备编制 ≤ 平台目录）。
2. **数据落盘为 `mission_input.json`**：新增 Pydantic 模型 `MissionInput`（见 §3.1、§4.1），作为推演与清单的唯一输入契约；保留 YAML 作为"标准模板库"，GUI 录入结果为其运行时覆盖。
3. **标准项字典**：从 `param_catalog.yaml` 抽出"装备/弹药/油料/器材/保障车辆标准目录"，前端下拉直接引用，避免自由文本。
4. **修复语义混乱**：把地形/天气/能见度/风场控件明确标为"预览/回放生效，实时推演沿用想定值（保持权威数字）"，或提供"强制覆盖（会改变结果，需重标定）"开关并二次确认。

### 2.3 推演编排改造（B 层）

1. 新增 `runner.run_mission(input: MissionInput, n_runs: int) → MissionResult`，内部调用现有 `run_replications`，但把"每次复制的事件流/快照"保留下来供清单层使用。
2. 输出统一的 `runs_detail.csv`（每次复制的四率 + 完成率）与汇总 `summary.json`（均值/std/CI）。
3. **不改** `four_rates.py` 的公式，只在清单层复用同一份事件流，保证"清单"与"四率"同源。

### 2.4 战损清单层改造（C 层）

1. 新增 `experiment/battle_loss.py`：
   - `build_loss_list(snapshots_df, engagements_df, state_final, platform_catalog) → LossList`：逐单位生成清单行（字段见 §3.2）。
   - `aggregate(loss_list, group_by=[side,platform,grade,disposition]) → loss_summary`。
   - `rates_from_loss_list(loss_summary, roster) → four_rates`：按 §4.3 口径，**校验与 `four_rates_summary()` 的差异在容差内**（防止两套口径打架）。
2. 落盘 `battle_loss_list.json`（机器可读）+ `battle_loss_list.csv`（人可读可上报）+ `loss_summary.json`。
3. 大屏新增"战损清单"视图：可筛选方别/装备/等级/处置，导出 CSV。

### 2.5 方案生成层改造（D 层）

1. **模板管理**：新增 `templates/plan/` 目录，存放"正式模板"（`.md`/`.docx`），模板中用 `{{slot_id}}` 标记槽位；提供"槽位字典"（§4.4 附）声明每个槽位的数据来源（清单汇总/推演汇总/决策变量/人工填写）。
2. **确定性填充**：新增 `plan/slot_filler.py`，把数值型槽位从 `loss_summary`/`summary.json`/`decisions` 填入——**数字一律不由 LLM 生成**。
3. **LLM 叙述生成**：扩展 `llm_client.py` 支持 `response_format={"type":"json_object"}` 或结构化输出；按模板章节分段调用，每段 system prompt 注入"只能引用给定数据、不得编造数字"铁律（沿用现有 `_LLM_SYSTEM_PROMPT`）。
4. **一致性校验**：新增 `plan/validator.py`，扫描生成文本中的数字，与槽位数据比对，不一致则回退到"确定性填充 + 模板占位说明"。
5. **渲染导出**：复用 `report/build_report_docx.py` 的 md→docx 管线，产出可签发方案。
6. **API**：新增 `POST /api/plan/from-loss-list`（见 §4.6）。

### 2.6 不改边界（红线）

- 不改 `four_rates.py` 公式、`experiment/metrics.py` 口径、`docs/data-interface.md` 权威数字。
- 不改仿真内核的战损/处置逻辑（`combat/damage.py`、`sustainment/*`）——清单从其输出派生。
- 不改代理模型、Pareto、Sobol、仿真守卫、可视化与回放链路。
- 油料若一期进内核会改变四率分母与结果 → **一期只在方案层建模，二期单独立项并重新标定**。

### 2.7 分期实施建议

| 期 | 内容 | 交付物 |
|---|---|---|
| 一期（P0） | A 层录入界面 + `mission_input.json`；C 层战损清单 + 口径对账；D 层模板 + 槽位填充 + LLM 叙述 + 校验 | 可录入→可推演→出清单→出方案闭环 |
| 二期（P1） | 油料链进内核；日常业务要素；G5 语义修复；清单视图导出 | 全要素对齐 |
| 三期（P2） | 通用物资 SKU、时变保障输入、每次复制明细落盘 | 完整支撑 |

## 3. 关键数据项

### 3.1 输入数据项（`MissionInput`）

| 组 | 字段 | 类型 | 必填 | 对应现有 schema | 说明/示例 |
|---|---|---|---|---|---|

### 4.3 战损率计算规范（★必须先定口径★）

**问题的答案**：战损率等指标**应当且可以由战损清单派生**，这样清单成为唯一事实源，可人工复核、可上报；但必须沿用现有口径的"只认 K 级战毁"定义，否则会改变权威数字。给出两套口径，推荐 A：

| 方案 | 战损率定义 | 与现有权威数字关系 | 建议 |
|---|---|---|---|
| **A（推荐）** | `战损率 = 清单中 K 级战毁数 / 参战装备总数`；M/F 单列为"战斗损伤率"，不并入战损率 | 与 `four_rates.py` 的 `1-alive_n/n` **完全一致**（alive=False 即 K 级） | ✅ 采用。清单按 grade 分组后直接算，且与现有四率对账 |
| B | `战损率 = (K+M+F) / 参战总数`（含可修复损伤） | 会显著抬高战损率，改变 0.650 完成率语境下的所有结论 | ❌ 不采用，除非你明确重定义并接受重标定 |

**由清单派生的指标口径（推荐 A）**：

```
参战总数 N        = roster 中该方初始装备数（与 n_by_side 一致，含 apply_features 新增保障车）
K 战毁数          = count(grade == K)
M 机动受损数      = count(grade == M)
F 火力受损数      = count(grade == F)
战损率 attrition  = K / N                         ← 与现有 attrition 等价
战斗损伤率        = (K+M+F) / N                   ← 新增，单列
完好率 readiness  = (N - K - M - F - 在修) / N     ← 需 snapshot 口径，与现有一致
修复率 repair_rate= 已修复数 / 应修数               ← 与现有 repairs_done/required 一致
故障率 failure_rate= 自然故障数 / 暴露量            ← 与现有口径一致
```

**对账要求**：`rates_from_loss_list()` 的结果与 `four_rates_summary()` 逐项比较，战损率/完好率差异 ≤ 1e-6，修复率/故障率差异 ≤ 1e-3（因清单粒度/取整不同）；否则报错并阻断清单输出。这样"清单"与"报告数字"永不打架。

### 4.5 模板→LLM→最终方案的生成机制

```
正式模板(.md/.docx) ─①解析→ 章节结构 + 槽位清单
        │
        ├─②槽位字典映射：每个 slot_id → {source, extractor, unit}
        │
战损清单/推演数据 ─③确定性填充→ 数值槽位（数字禁止由 LLM 生成）
        │
        ├─④分段 prompt：system(铁律) + user(该章模板+已填数据+清单摘要+写作要求)
        │
LLM(Qwen3) ─⑤叙述生成→ 叙述槽位（每段 JSON：{slot_id: text}）
        │
        ├─⑥一致性校验：正则抽取文本数字 ↔ 数据槽位，不一致→回退占位说明
        │
        └─⑦渲染：合并槽位 → 完整 .md → build_report_docx.py → 可签发 .docx
```

**关键设计点**：
1. **数字与文字分离**（最重要）：所有数字槽位由 `slot_filler` 从数据确定填入；LLM 只写"情况判断、决心、原则、措施"等叙述。**防止 LLM 编数字**——这是现有 `_LLM_SYSTEM_PROMPT` 铁律的制度化。
2. **扩展 `llm_client.chat()`**：增加 `response_format={"type":"json_object"}`（vLLM/Ollama 普遍支持），要求返回 `{slot_id: text}` 的 JSON；失败降级为纯文本分段解析。
3. **分段生成**：按模板章节逐段调用，避免一次生成过长导致结构漂移；每段传入该章相关的清单摘要，保证"战损判断"章节确实引用清单数字。
4. **校验器**：`validator.py` 扫描叙述中的百分数/数量，若出现在数据槽位集合中但数值不符，替换为"[待核：数据槽位值 X]"并记日志。
5. **降级路径**：LLM 不可用时（`mode=auto` 会降级），用"确定性填充 + 模板默认叙述句"产出可用方案，不阻断业务。
6. **模板替换**：换正式模板只需替换 `.md/.docx` 并保持槽位 ID 一致；槽位字典提供"未匹配槽位"提示， humans 可人工补填。
