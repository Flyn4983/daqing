## 0. 结论摘要

P2 的 7 项全部落地并通过浏览器端到端实测。**没有重构顶栏导航**：按规划 §6 第三批"视需要"，考虑用户一贯强调的"核心流程零风险"，本批次把新能力挂在既有 8 节点流程条与三栏主结构的增量容器内（回退重算条、方案工具按钮、档案模态、独立模态），主网格与权威数字一个不动。

需要强调三点边界：
1. **批量工况对比（P2-1）不重新推演**，只聚合已落盘档案；未推演的工况单列为 `not_deduced`，绝不被误读为零战损。
2. **方案版本对比（P2-2）与签批流（P2-3）** 复用已存在的多方案落盘档案，未新增"方案生成逻辑"，只是把它们可视化。
3. **成本权重（P2-5）不进内核**：只在录入—方案层归一与展示，四率权威数字完全不受影响。

## 2. 关键实现约定

### 2.1 批量工况对比只读档案（P2-1）

`compare_scenarios()` 扫 `outputs/support/loss/loss_*.json`，每个 scenario 取最近一次（mtime 最大）清单：

```json
{
  "scenarios": [{"scenario":"example_brigade","attrition":0.146,"readiness":0.417,
                 "terrain":"按想定地形","weather":"晴空","source":"archive", ...}],
  "not_deduced": ["brigade_plain_fog", ...],
  "count": 2,
  "note": "对比来自已归档推演，未重新推演；not_deduced 工况没有档案，不代表零战损。"
}
```

**不做重推演**的理由：八工况各跑一次 MC 在 ARM 上耗时可观，且与"权威数字冻结"冲突——对比视图定位为"已做过的工况横向看"，不是批量实验台。

### 2.2 方案版本 diff（P2-2）

- 槽位差异：对每份方案的 `slots` 逐 key 比对，仅列出取值不全相同的槽位（label 取 `SLOT_DICT`）；
- 正文差异：`difflib.unified_diff` 行级对比，最多回传 400 行，避免大方案撑爆前端；
- 选方案数 2~4，方案列表来自 P1-8 落盘档案。

### 2.3 签批状态机（P2-3）

状态转移严格校验（在 `REVIEW_ACTIONS` 中定义）：

```
draft ──提交复核──► reviewing ──复核定稿──► approved
  ▲                    │                      │
  └──────退回修改──────┘                      └──重新复核──► reviewing
```

- 非法跃迁（如 draft 直接 approve）后端返回 error，不落盘；
- 每次流转追加 `review_log`（动作/来源/目标/备注/时间），方案 JSON 原地更新；
- 状态条只渲染当前状态的合法动作，用户不会点到无效操作。

### 2.4 成本权重零漂移（P2-5）

`mission_input.validate` 对 `cost_weights`：
- 每项按 `COST_WEIGHT_SPEC` 的 min/max 钳制，坏类型抛 `ValueError`；
- 三项相对权重归一到和为 1（避免乱填失真），`budget_limit` 保持整数；
- **不进入 `to_run_config()`**——即不映射为 7 个推演旋钮，`getattr(sc, ...)` 链路不变；
- 仅方案层与对比视图可展示，四率 R²=0.705 / 加速比 38 万倍 / 战损率口径完全不变。

### 2.5 回退重算的诚实边界（P2-7）

`recompute_from()` 只支持 **rates / plan / review** 三个下游环节（纯派生，秒级）：

| stage | 行为 | 是否重跑仿真 |
|---|---|---|
| rates | 从战损清单重派生四率（`rates_both_doctrines`）并落新清单 | 否 |
| plan | 从当前任务/清单重新生成方案（数字槽位确定性重填） | 否 |
| review | 对现有方案重跑数字一致性复核 + 溯源 | 否 |
| input/validate/deduce/loss | 返回 error 提示"需重跑仿真" | 是（走"开始多次推演"） |

这不是"真回退执行引擎"——它是**结果层的下游重算**，解决"改口径/改阈值/改模板后不必从头推演"的实际诉求；涉及战场状态变化的环节老老实实重跑。

### 2.6 两个数据字典入口（P2-4）

顶栏「数据字典」供未开抽屉时查阅，抽屉内「数据字典」供作业中使用。因字典模态在抽屉 DOM 内（`position:absolute`），顶栏入口点击时先调 `open()` 确保抽屉可见，避免模态显示在屏幕外。

## 5. 已知边界与待确认

1. **导航未重构**（规划 §4.3）：本批次按用户"核心流程零风险"的约束，采用增量承载而非四区分层导航。若后续要做 P2-1 的"真·批量实验台"（八工况各重跑 MC），建议按 §4.3 重构导航并新增"作业档案/对比"视图。
2. **部署示意图是数据驱动的示意，非真实 3D 部署**：节点与连线依据方案数字槽位（抢修组数/抢救车数/器材车数等）自动绘制；真实地形与单位位置见 3D 态势回放（P1-4 清单定位）。
3. **批量对比依赖档案完整性**：只有做过多次推演并落盘的工况才出现在对比表；`not_deduced` 明确列出未推演工况，避免误读。
4. **签批状态无权限体系**：当前为演示级状态机（动作按钮按状态显示），未接入用户角色与数字签名；如需正式公文流转，需叠加认证与审计。
5. **成本权重仅为展示维度**：未接入 Pareto 的 cost 维度做重排序（那会碰优化内核，违背零改动红线）；当前用于方案评估的权重录入与归一化展示。
